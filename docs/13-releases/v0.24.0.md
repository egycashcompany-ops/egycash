## 1. What shipped

### Recruitment Workflow Refactor — the headline

The frozen design `docs/12-planning/recruitment-workflow-design.md` (Revision 2.6 — decisions
RW1–RW17, invariants I1–I15) is implemented in full. The changes worth an operator's attention:

- **Placement is a first-class field on the applicant** (RW1–RW5). Position, title, department,
  branch and section stay editable from Screening through Offer Acceptance, and moving a
  candidate is its own audited action (`applicant.reassign`) with a mandatory reason — never a
  silent field edit. Acceptance freezes the placement, because it is what the Employee, Contract
  and Payroll records descend from.
- **Return to a previous stage** (RW13) re-attempts rather than rewrites. Nothing is deleted or
  modified: forward stages are marked `supersededAt` and a new attempt opens at the target.
- **One chronological history** (RW14/I5). `hr_recruitment_timeline` is the only history any
  screen reads, including the Electronic Employee File.
- **`waiting` is a real row** (I11). Every stage always has a record, so queues, counters and
  badges are plain indexed reads over explicit statuses rather than derivations over rows that
  do not exist.
- **One workflow engine owns every transition** (I13), enforced mechanically: stage repositories
  reject `status`, `attempt`, `supersededAt` and `placementSnapshot` unless the caller holds the
  engine's token.
- **Every mutation answers with the full state** (I6): `{ data, workflow, timeline, counters }`.
  The web client applies that envelope to its cache and issues **no follow-up request**.
- **Batch workflow for Security and Driving checks** (RW8) with a generated PDF package and ZIP
  export; Medical stays individual (RW9).
- **Employees Ready** queue and bulk actions on every recruitment table (RW10/RW17).

### Employee Management

The employee registry, employment lifecycle (probation-first), personnel actions with

### Leave Management

### Platform & Organization

Management UI Phase 3, the organization reference-options endpoint, and Railway deployment
support.

## 2. Upgrading

**No manual step is required.** Every migration is idempotent and runs automatically at boot
(I8), so a deploy is the whole upgrade procedure. Re-running them changes nothing, which is what
makes them safe on every restart.

What the boot migration does for recruitment data:

| Step | Effect on existing data |
|---|---|
| Attempt markers | `attempt: 1`, `supersededAt: null` backfilled on every stage record |
| `pending` → `waiting` | Stored status values renamed on screenings and evaluations; `pending` stays accepted as a query alias for one release |
| Placement backfill | `placement` / `placementLabel` / `placementHistory` populated from the applicant's branch |
| Evaluation phase typing | `phaseKind` and business-order re-sequencing |
| Offer terms | Nullable draft fields normalized |
| **Waiting backlog** | **Every live applicant gains the `waiting` row their position already implies** |

That last step matters most on an existing database: before it, an applicant who moved through
the pipeline under the old model has no row at the stage they stand at, and since `waiting` is
now a persisted value rather than an absence, they would be invisible to every queue, counter
and badge. The migration resolves each live candidate's position from their own records and
opens what is missing. Applicants who are `withdrawn` or `rejected` are deliberately left out —
withdrawal is a lifecycle terminal and nothing re-admits them to a queue.

**Expect a longer first boot** proportional to the number of live applicants. Subsequent boots
repair nothing and cost a single indexed scan.

## 3. New scheduled tasks

Three recovery paths now run without an operator:

| Task | Cadence | What it repairs |
|---|---|---|
| `hr.recruitment.workflowOutbox` | every 5 min | Workflow events that committed but whose publish never ran (process killed between commit and dispatch) |
| `hr.recruitment.timelineReconcile` | hourly | Timeline entries that should exist and do not — unprojected events, plus `applied` / `identityVerified`, which have no event behind them |
| Waiting-row backfill | every boot | Stage rows a candidate should stand on but does not |

All three are safe to overlap and safe to repeat. A run against a healthy database writes
nothing.

## 5. Known limitations

- **Batch-level history.** Evaluation-batch actions that span every candidate in a batch
  (create, add/remove members, issue, upload results, close, cancel) return the partial-success
  envelope but no per-candidate `workflow` state, because a batch has no single candidate whose
  state to report. Reporting a batch's own history *as a batch* needs a read that is not
  per-applicant; it is tracked as a separate design proposal, not a missing line of code.
- **`pending` query alias.** Accepted for one release on evaluations and screenings so existing
  deep links keep working. It should be removed in the next release.
- **Sprint retrospectives 5.12 onward were not written at the time.** The capabilities in this
  release other than the Recruitment refactor shipped without their own retrospective; only
  [the Recruitment Workflow Refactor retrospective](../11-retrospectives/2026-07-recruitment-workflow-refactor.md)
  exists.
